# RiftCity Hybrid JavaScript + React Roadmap

## Decision

RiftCity is moving to a **hybrid frontend**, not a React rewrite.

The real-time 2.5D game runtime stays in plain JavaScript. React is introduced only where
component/state-driven UI gives a clear maintenance advantage. Cloudflare Workers, D1,
server-authoritative gameplay, routing contracts and existing APIs remain unchanged.

## Ownership boundary

### Plain JavaScript owns permanently

- 2.5D block runtime and scene lifecycle
- requestAnimationFrame movement loop
- camera positioning and block traversal
- collision and walkable geometry
- joystick, touch, mouse and keyboard input
- fullscreen/orientation handling
- object dragging/hit testing in world space
- neighboring-block loading/preloading
- low-level asset/scene rendering
- Worker/API backend and D1 persistence

These systems are timing-sensitive and imperative. Moving them into React state would add
render overhead and make mobile debugging harder without providing a useful benefit.

### React owns now

**Block Editor interface**

React owns the editor's UI structure: inspector, position/size inputs, quick actions,
asset controls, minimize/close controls and mobile responsive editor shell.

During the transition, the existing Block World runtime still owns editor behavior and
updates the React-rendered DOM through the existing element contract. This intentionally
avoids changing movement/collision/fullscreen code at the same time as the UI migration.

### React should take over next

1. Reusable modal/dialog system and toast surfaces.
2. HUD presentation and effects/resource strips.
3. Inventory view and item inspector.
4. Crime cards, filters, approaches and inline results.
5. Service-heavy interfaces: bank, jobs, education, properties, market and production.
6. Casino interface components.
7. Character/progression dashboards.
8. Navigation/drawer/mobile shell after the individual React views are proven stable.

### Keep outside React even after migration

The actual playable city canvas/block DOM, player transform updates, camera transforms,
collision checks, touch joystick state and fullscreen rotation stay plain JS.

## Bridge design

React and the game runtime communicate through a narrow boundary.

Current transition:
- React mounts UI controls.
- The game runtime attaches behavior to the existing control IDs.
- React does not receive frame-by-frame player coordinates.

Target bridge:
- runtime emits semantic events such as `selectionchange`, `editmodechange`,
  `fullscreenchange` and `blockchange`;
- React calls explicit runtime commands such as `moveSelection`, `resizeSelection`,
  `undo`, `redo`, `exportBlock` and `setSnap`;
- no React state updates are performed every animation frame.

## Build layout

```text
client/
  react/
    index.jsx
    BlockEditor.jsx

public/
  react-ui.js       # generated by npm run build:react
  views/
  ui/
  ...

src/
  ...               # Cloudflare Worker/backend remains plain JS
```

`esbuild` bundles the React island into `public/react-ui.js`. Wrangler continues serving
`./public`, so Cloudflare deployment architecture does not change.

## Migration phases

### Hybrid H1 — Foundation + Block Editor (current)

- Add React + ReactDOM.
- Add esbuild as the tiny React build step.
- Keep the existing Wrangler/public deployment path.
- Mount the Block Editor as the first React island.
- Preserve the current mobile portrait/fullscreen editor behavior.
- No backend, routing, gameplay or database changes.

Exit criteria:
- Block Editor works on iPhone Safari portrait.
- Block Editor works in iPhone CSS-rotated fullscreen.
- Samsung/Android native landscape fullscreen works.
- Touch, mouse/trackpad and keyboard editing all work.
- Play-mode joystick/RUN/ENTER remain unaffected.

### Hybrid H2 — Shared UI primitives

Create React components for:
- modal/dialog
- confirmation sheet
- tabs
- segmented filters
- loading/error/empty states
- toast/result surfaces

Do not migrate entire pages yet.

### Hybrid H3 — Inventory + Crimes

Move the two most state-heavy normal pages to React while reusing the current API helpers.
Server responses remain authoritative; React only presents and submits actions.

### Hybrid H4 — Service pages

Migrate finance/progression/economy service interfaces by feature, not as one giant rewrite.

### Hybrid H5 — HUD + shell

After several React views are stable, move HUD, drawer and mobile navigation to React.
Hash route compatibility remains until a later explicit routing decision.

### Hybrid H6 — Cleanup

Remove superseded imperative UI rendering only after its React replacement is proven.
Do not delete plain-JS game/runtime modules.

## Rules for future patches

1. Never rewrite working game-runtime code merely to make it "more React."
2. Do not put frame-by-frame position/camera values in React state.
3. One system migrates at a time and must remain deployable after each phase.
4. Mobile Safari is a first-class test target, not a desktop-afterthought.
5. Fullscreen portrait fallback and Android landscape must both be tested.
6. Server-authoritative outcomes stay on the Worker.
7. React components may call APIs, but never calculate authoritative rewards/results.
8. TypeScript is not part of this migration. JSX remains JavaScript.
9. Existing URL/hash routes remain stable during the hybrid migration.
10. Each migrated screen removes its old duplicate UI only after validation.

## Why not a full React rewrite?

RiftCity already has a working JavaScript backend and an imperative real-time city runtime.
A full rewrite would combine unrelated risks: rendering, input, camera, routing, mobile
fullscreen and UI migration. The hybrid boundary lets React improve the parts it is good at
without touching the game loop that is better served by direct JavaScript.
